## 1. 複数ノートブック横断検索

**課題**: NotebookLM の質問は 1 ノートブック単位。テーマごとにノートを分けると、
「どのノートに聞けばいいか」を人間が覚えている必要がある。
ソース数の上限（アカウント階層依存）があるため、分割は避けられない。

**実装方針**:

1. ノートブックのメタデータ（名前 / 説明 / トピック / タグ）をローカル台帳に持つ
   - notebooklm-mcp は `library.json` として既にこれを持っており、`search_notebooks` もある
   - notebooklm-py 側は `notebooklm metadata --json` の出力を自前で集約する
2. 質問が来たら、まず台帳をキーワード / 埋め込みでルーティングして候補ノートを 1〜3 件選ぶ
3. 選ばれたノートに並列で `ask --json` を投げる
4. 回答をマージし、**ノートブック名を出典に含めたまま** 提示する

**難所**:
- 回答が矛盾したときの扱い。マージで平均を取らず、「N1 はこう、N2 はこう」と併記する設計にする
- 並列実行はプロファイル分離（`NOTEBOOKLM_PROFILE=agent-<id>`）が必須。共有コンテキストファイルの競合を避ける
- レート制限。無料アカウントは日次上限があるため、横断検索は 1 質問で複数消費する点に注意

**最小実装**: 台帳を YAML 1 枚（`notebooks.yaml`: id / name / topics / tags）で持ち、
Codex に「質問前に notebooks.yaml を読んで対象を選べ」と AGENTS.md で指示するだけでも実用になる。

## 2. 自動ソース更新

**課題**: 登録した Web ドキュメントは登録時点のスナップショット。上流が更新されても追随しない。

**実装方針**:

1. ソース一覧を宣言的に持つ（`sources.yaml`: URL / 更新頻度 / 最終取得日時）
2. 定期ジョブで各 URL の `Last-Modified` / `ETag` / 本文ハッシュを確認
3. 変化があったソースだけを差し替える
   - notebooklm-py に **ソース refresh** の機能があるため、削除→再登録より軽い
4. 差分を要約して通知する（`ask` で「前回から何が変わったか」を聞く運用も可）

**難所**:
- 全ソースの再登録はレート制限に直撃する。差分検出は必須
- SPA や動的生成ページはハッシュが毎回変わる。ヘッダベースの判定を優先する
- 「更新されたので回答が変わった」ことを利用者に伝える導線が要る

**cron 例**:

```bash
# 毎週月曜 4:00 に更新チェック
0 4 * * 1 cd /path/to/repo && ./scripts/refresh-sources.sh >> logs/refresh.log 2>&1
```

## 3. ノートブック・レジストリ（このリポジトリ内）

**課題**: ノートブック ID が各人のシェル履歴や `notebooklm use` の暗黙状態に散っている。
チームで共有できず、並行エージェントで壊れる。

**実装方針**: リポジトリに `notebooks.yaml` をコミットし、ID を明示的に管理する。

```yaml
notebooks:
  - key: project-brain
    id: "<notebook-id>"
    purpose: 設計判断の永続メモリ
    sources: docs/, ADR
  - key: lib-docs
    id: "<notebook-id>"
    purpose: 依存ライブラリのドキュメント・オラクル
    refresh: weekly
```

エージェントには「`notebooklm use` を使わず、必ず `--notebook <id>` を明示する」と指示する。
これだけで並行実行時の取り違えがなくなる。

**注意**: ノートブック ID 自体は秘密情報ではないが、共有 URL は閲覧権限に直結する。
公開リポジトリに置く場合は ID の公開範囲を確認する。

## 4. 定期ブリーフィング

**課題**: 情報の取り込みが手動起動に依存している。

**実装方針**: `auth refresh --quiet` で認証を維持しつつ、生成をスケジュールする。

```bash
# 毎朝 7:00：前日追加されたソースから音声ブリーフィングを作る
0 7 * * * notebooklm auth refresh --quiet && \
          notebooklm generate audio "昨日追加された内容だけを 5 分で" --wait --notebook <id> && \
          notebooklm download audio ~/briefings/$(date +\%F).m4a --notebook <id>
```

上流の機能だけで完結します。macOS は launchd、Windows はタスク スケジューラで同等のことができます。

**発展**: 生成した音声を private な RSS フィードに置けば、通勤中にポッドキャストとして聞けます。

## 5. 引用の相互リンク化

**課題**: NotebookLM の回答に付く `[1]` のようなマーカーが、ローカルのファイルや
ナレッジベースの該当箇所に繋がっていない。

**実装方針**:

1. `ask --json` の `sources[]`（title / excerpt / url）を取得
2. ソース登録時に記録した「元ファイルパス ↔ NotebookLM ソース ID」の対応表と突き合わせる
3. 回答内のマーカーを、Obsidian の `[[wikilink]]` や GitHub のパーマリンクに置換して保存

**難所**: 引用の抜粋テキストからローカルの行番号を特定するのは曖昧マッチになる。
ソース単位のリンクに留め、行単位は目標にしないのが現実的。

## 6. フォールバック多重化

**課題**: notebooklm-py / notebooklm-mcp はどちらも非公式で、上流の仕様変更で突然壊れうる。

**実装方針**: 2 系統を別名の MCP サーバーとして両方登録し、片方が失敗したらもう片方に切り替える。

```bash
codex mcp add notebooklm         -- uvx --from "notebooklm-py[mcp]" notebooklm-mcp
codex mcp add notebooklm-browser -- npx notebooklm-mcp@latest
```

AGENTS.md に「`notebooklm` が認証・RPC エラーを返したら `notebooklm-browser` を試す」と書く。
両者は**壊れ方が独立している**（内部 RPC の変更 vs UI の変更）ため、
同時に落ちる確率は低くなります。

**注意**: バイナリ名が両方 `notebooklm-mcp` で衝突します。
必ず `uvx --from` / `npx` の形で明示してください（[02-setup-codex.md](02-setup-codex.md#3-a-mcp-サーバーとして登録対話利用向け)）。

## 7. コスト / 使用量の可視化

**課題**: 「トークン 70% 削減」の効果が体感でしか分からない。NotebookLM 側のクエリ上限も見えない。

**実装方針**:

- `ask` を薄いラッパー経由にして、質問 / 回答文字数・所要時間・ノートブックを JSONL に追記
- 週次で集計し、「NotebookLM に投げた回数」「返ってきた回答の総量」「直接読ませていたら
  かかったであろう概算」を出す
- 併せて日次クエリ数を数え、無料枠の上限に近づいたら警告する

削減率は**元のソース総量に強く依存する**ため、単一の固定値を目標にせず自分の環境で実測してください
（[03-comparison.md](03-comparison.md#トークン効率の実際)）。

## 8. CI への組み込み

**課題**: ドキュメントと実装の乖離を人手でしか検出できない。

**実装方針**: master-token 認証（無人で自己修復する）を使い、CI から問い合わせる。

- PR で公開 API が変わったら、仕様ノートブックに「この変更はドキュメントと整合するか」と質問し、
  食い違いがあれば PR にコメントする
- リリースノートの草稿を、変更ログを登録したノートブックから生成する

**難所**:
- 認証情報を CI シークレットに置く必要がある。`master_token.json` は Google アカウントへの
  実質的なアクセス権なので、専用のサービス用アカウントを使い、本番アカウントを使わない
- 非公式 API のため CI が不安定になりうる。**必須チェックにしない**（`continue-on-error`）

## 実装しないほうがよいもの

| 案 | 理由 |
|---|---|
| 独自の NotebookLM クライアント実装 | 要件 §5「車輪の再発明を避ける」に反する。上流 2 本で足りる |
| 回答のローカルキャッシュ（無期限） | ソース更新後も古い回答を返す事故につながる。TTL を切るなら可 |
| NotebookLM 回答の自動コード適用 | 生成物は検証されていない。必ず人間かテストを挟む |
| 複数 Google アカウントでのレート制限回避 | 利用規約上のリスクがある。上限に不足があるなら有料プランで解決する |
